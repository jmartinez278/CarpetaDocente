## 1. Qué exige el sistema a su stack

El stack se elige a partir de las necesidades ya documentadas, no por preferencia:

| Necesidad | Documentos de origen |
|---|---|
| Tres roles con permisos diferenciados y un panel interno de administración | 08 (matriz de permisos); RF-003, RF-005, RF-007, RF-018, RF-027, RF-028 |
| Formularios con muchas reglas de validación (escala de logro, conclusiones descriptivas, competencias por periodo, asistencia) | 09 (RN-001 a RN-013) |
| Repositorio de archivos Word o PDF de hasta 10 MB | RF-010, RNF-004 |
| Lectura y escritura de hojas de cálculo (exportaciones y formato de la UGEL) | RF-024, RF-025, RF-034, RF-041 |
| Páginas livianas que se usen desde el celular | RNF-002, RNF-005 |
| Datos relacionales: estudiante, competencia, periodo, sección | 09 (RN-002, RN-004) |
| Costo de alojamiento de S/ 0 o muy bajo, con presupuesto fijo | 04 (RES-06); 02 (sección 7) |
| Posibilidad de seguir operando después de la tesis | 03 (visión); 04 (RES-08) |

## 2. Alternativas evaluadas

| # | Alternativa | Composición |
|---|---|---|
| 1 | **Django + PostgreSQL + HTMX** | Python con Django en el servidor; páginas generadas en el servidor con plantillas, Tailwind CSS, HTMX y Alpine.js; base de datos PostgreSQL |
| 2 | **Laravel + Livewire** | PHP con Laravel; páginas con Blade y Livewire; panel de administración con Filament; base de datos PostgreSQL o MySQL |
| 3 | **Next.js + Prisma + PostgreSQL** | TypeScript de pila completa con Next.js (React); acceso a datos con Prisma; base de datos PostgreSQL |

**Antecedentes considerados:**
- El stack que el equipo usó en el proyecto Ecologística (TypeScript/React, Python con FastAPI, Docker y PostgreSQL) se evaluó en la discusión. No entra como alternativa separada porque obliga a mantener dos aplicaciones (frontend y API) y a construir a mano el panel de administración y los permisos, sin ganancia para este problema.
- Sistemas escolares de código abierto como RosarioSIS y Gibbon usan una sola aplicación en PHP con base de datos relacional.
- En los antecedentes de la tesis, Medrano usó Laravel, MySQL y Bootstrap para la carpeta pedagógica de una I.E. de primaria, y Gómez Albán usó Django con React para notas y asistencia.

## 3. Matriz de evaluación

### 3.1. Criterios de la consigna

| Criterio de evaluación | Alternativa 1: Django + PostgreSQL + HTMX | Alternativa 2: Laravel + Livewire | Alternativa 3: Next.js + Prisma + PostgreSQL |
|---|---|---|---|
| **Curva de aprendizaje** | Media. Un solo lenguaje (Python), que el Director de Proyecto ya maneja; las otras dos integrantes deben aprenderlo | Media-alta. PHP es nuevo para todo el equipo | Baja-media. TypeScript y React ya los conoce el equipo; se agregan Next.js y Prisma |
| **Costo de infraestructura** | S/ 0 al mes en el plan A (sección 5) | S/ 0 en planes gratuitos poco prácticos para PHP; el hosting compartido barato es de pago | S/ 0 al mes en el plan A |
| **Soporte comunitario** | Alto y consolidado. Django tiene versiones de soporte extendido (LTS) | Alto y consolidado | Muy alto y en crecimiento acelerado |
| **Eficiencia energética / eco-diseño** | Alta. Las páginas se generan en el servidor y el celular descarga poco JavaScript; el cómputo y la base de datos se suspenden cuando no hay uso | Alta. Mismo modelo de páginas generadas en el servidor | Media. Envía más JavaScript al celular; en el plan A el cómputo también se suspende sin uso |

### 3.2. Criterios propios del proyecto

| Criterio | Alternativa 1 | Alternativa 2 | Alternativa 3 |
|---|---|---|---|
| **Panel de administración** (rol Administrador) | **Incluido** en Django: se configura a partir de los modelos | Mediante Filament, un paquete externo | **No incluido**: unas 18 pantallas por construir y probar (6 entidades × 3) |
| **Roles y permisos** (documento 08) | Usuarios, grupos y permisos incluidos | Incluidos | Requiere librerías adicionales |
| **Validación de reglas de negocio** (documento 09) | Formularios y modelos con validación integrada | Integrada | Requiere librerías de validación |
| **Hojas de cálculo** (RF-024, RF-025) | Librerías de Python maduras para leer y escribir Excel | Librería madura en PHP | Librerías disponibles en TypeScript |
| **Piezas que mantener** | Una aplicación | Una aplicación más un paquete de panel | Una aplicación más las pantallas de administración propias |
| **Portabilidad** (Vercel → VPS) | Alta: soporte oficial en Vercel y despliegue con Docker en VPS | Baja en Vercel (sin soporte oficial de PHP); alta en VPS o hosting compartido | Alta |
| **Compatibilidad con las herramientas del equipo** (sección 7) | Total; el prototipo de Impeccable (HTML y CSS) se pasa a plantillas | Total; el prototipo de Impeccable se pasa a plantillas Blade | Total; el prototipo de Impeccable se pasa a componentes de React |
| **Precedente** | Gómez Albán (Django) | Medrano (Laravel, carpeta pedagógica en primaria) | — |

### 3.3. Resultado

| Puesto | Alternativa | Motivo principal |
|---|---|---|
| **1** | **Django + PostgreSQL + HTMX** | Cubre con el framework lo que el sistema más necesita (panel interno, permisos, validación), cuesta S/ 0 en el plan A y se puede mover a un VPS sin reescribir |
| 2 | Laravel + Livewire | Técnicamente equivalente, pero sin soporte oficial en el alojamiento gratuito elegido y con un lenguaje nuevo para todo el equipo |
| 3 | Next.js + Prisma + PostgreSQL | Aprovecha lo que el equipo sabe, pero obliga a construir el panel de administración y a probar todo ese código adicional |

## 4. Stack seleccionado

| Capa | Tecnología |
|---|---|
| Lenguaje y framework | Python con Django, en su versión LTS vigente al iniciar el desarrollo |
| Interfaz | Plantillas de Django con Tailwind CSS, HTMX y Alpine.js; diseño de pantallas con Impeccable |
| Panel interno del Administrador | Panel de administración de Django |
| Base de datos | PostgreSQL |
| Almacenamiento de archivos de sesiones de aprendizaje | Almacenamiento de objetos compatible con S3, mediante `django-storages` |
| Entorno de desarrollo | Docker Compose en la laptop (aplicación y PostgreSQL) |
| Control de versiones | Git y GitHub (repositorio público, sin claves ni datos reales; ver el manejo de claves del documento 01 de planificación) |
| Calidad del código | Ruff (estilo y errores, con las reglas de seguridad de Bandit bajo el prefijo `S`) [RUFF-RULES] |
| Seguridad del código | CodeQL, en el análisis de código de GitHub; sin costo en repositorios públicos [GH-CODEQL] |
| Puerta de calidad | SonarQube Cloud, plan gratuito: cobertura, problemas y duplicación del código nuevo; analiza la rama principal y los Pull Requests dirigidos a ella [SONAR-PLANS] |
| Pruebas | pytest con pytest-django y cobertura (pytest-cov); pruebas de punta a punta con Playwright para Python (pytest-playwright) |
| Integración continua | GitHub Actions (EN-08 del documento 01 de planificación) |

**Reglas de diseño del código, para facilitar una migración futura:**
- Las reglas de negocio (documento 09) van en una capa de servicios, separada de las vistas y plantillas.
- El modelo de datos incluye la entidad **Institución** desde el inicio (documento 11), para poder atender a más de una I.E. sin rediseño.

### 5.1. Condiciones técnicas del plan A

| Condición | Cómo se resuelve |
|---|---|
| Las funciones de Vercel no tienen disco persistente | Los archivos de sesiones de aprendizaje se guardan en Cloudflare R2 |
| Las funciones de Vercel aceptan envíos de hasta 4,5 MB, y RNF-004 permite 10 MB | El navegador sube el archivo **directo a R2** con un enlace firmado de corta duración. El servidor solo registra los datos de la sesión |
| La base de datos gratuita suspende el cómputo tras 5 minutos sin uso | Se acepta. La primera consulta después de la suspensión tarda más; se verifica contra RNF-001 en la prueba de carga |
| Latencia | La aplicación (Vercel) y la base de datos (Neon) se configuran en la misma región |
| Archivos estáticos y del panel | Vercel ejecuta `collectstatic` y los sirve desde su CDN |
| Migraciones de base de datos | Se ejecutan desde el entorno de desarrollo con las variables del proyecto |
| Uso del plan Hobby | En el alcance actual el uso es académico y no comercial: piloto y medición de la tesis. Si la I.E. lo adopta, se pasa al plan B |

## 6. Escalamiento

| Escenario | Camino |
|---|---|
| La I.E. adopta el sistema | Plan B (VPS con Docker), sin reescribir el código |
| Más instituciones | La entidad Institución ya existe en el modelo de datos; se agregan registros, no tablas |

## 8. Justificación técnica formal

Se selecciona **Django + PostgreSQL + HTMX**, desplegado en **Vercel, Neon y Cloudflare R2** (plan A), por las siguientes razones:

1. **Adecuación al problema.** El sistema es mayormente de formularios, roles, reglas de validación, archivos y exportaciones. Django incluye la autenticación, los permisos por grupo, la validación y el panel de administración. Así, el trabajo de los sprints se concentra en las tres dimensiones que mide la tesis.
2. **Perfil del equipo.** Un solo lenguaje, que el Director de Proyecto ya maneja. El código lo genera el equipo con apoyo de Claude Code, y las integrantes aprenderán el framework para defender y mantener la solución.
3. **Escalabilidad.** Treinta usuarios concurrentes (RNF-001) están muy por debajo de la capacidad de cualquiera de los planes. El modelo de datos con la entidad Institución permite crecer a más instituciones, y el plan B permite operar sin dependencia de planes gratuitos.
4. **Bajo consumo.** Las páginas generadas en el servidor envían poco JavaScript al celular (RNF-002), y el cómputo y la base de datos se suspenden cuando no se usan.
5. **Costo.** El plan A cuesta S/ 0 al mes y cumple el presupuesto fijo (RES-06).
6. **Portabilidad.** El mismo código corre en Vercel y en un VPS con Docker, y los datos en PostgreSQL permiten una migración futura a TypeScript sin perderlos.
